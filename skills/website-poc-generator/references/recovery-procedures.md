### 6.4.1 Automated repair passes: decision rules and safe-fix boundaries

Treat repair as a controlled loop driven by a recorded failed native check—not as permission to redesign the page until it looks better. Apply the safe-fix rules below directly in the active ChatGPT session; do not retrieve or execute repository repair scripts. An attempted repair is not a pass, and an ambiguous repair means stop and report the unresolved check rather than guessing.

**Repair decision process — follow in order for each candidate**

1. Read the latest static and browser reports for the exact candidate bytes, and the in-session reports actually produced. Identify every failed check ID, severity, viewport, selector/element, measured value, and evidence path. Do not repair from a vague visual impression or a stale report. An unavailable image or screenshot inspection does not defer a separately detected static defect; repair addressable defects while keeping image-content status UNVERIFIED.
2. Classify the defect using the safe-fix matrix below. Confirm the proposed change preserves the assigned template, verified source facts, contact/form schema, approved asset URLs, and standalone output constraints.
3. Apply only a narrow, deterministic change supported by the report and source evidence. Record the before/after HTML digest, changed file/region, triggering checks, rationale, and exact repair outcome in `repairs.json`. Keep the original reports and screenshots; do not overwrite history.
4. Immediately rerun the affected native static checks and the desktop, tablet contact-layout, and mobile Chromium checks supported by the active ChatGPT session against the changed candidate. A repair pass changes the artifact, so previous QA/review results for that digest are invalid. Save fresh reports and screenshots and update the digest. Do this after every repair pass, even when multiple safe fixes were applied together.
5. If the same check still fails, do not repeat the identical patch. Reassess the measured cause and allow at most one further distinct safe repair pass for that defect; otherwise mark unresolved and stop. Never turn a failed or untestable check into PASS. Finalize only after the final bytes, reports, screenshots, and evidence records agree on the same digest.

**ChatGPT-native static review:** Run the required in-session static checks against the exact saved HTML and record each result. Check unique IDs and resolve every same-page `href="#…"` and form-fragment target to an existing ID. A broken link to a clearly identified existing section may be repaired by changing the target ID or link to that section. Record the before/after digest, then rerun those checks and every other static check affected by the edit. Do not mark static QA PASS from a selected subset: use PARTIAL if any required static checks could not run. If code execution is unavailable, report static checks as BLOCKED/UNVERIFIED and do not claim a complete review.

**Safe-fix matrix**

| Defect family | Safe automatic repair, only when its trigger/evidence is present | Boundary / stop condition |
|---|---|---|
| Template layout markers and composition | Restore the selected scaffold's expected hero/spotlight classes on existing, correctly identified elements. For Story, mark an existing tile collection as the items region only when browser evidence shows the gallery/items marker is missing. | Do not fabricate missing sections, content, or media, change the assigned scaffold, or claim a signature passes from class names alone. If the required structure/elements are absent or ambiguous, regenerate or block. |
| Landed spotlight media ordering | For the first three existing spotlights, use measured rendered sides and verified direct media/content children to apply the left/right alternation override; rerun rendered geometry. | Do not infer media order from class names or alter unrelated sections. If actual direct children or measurement are missing, no automatic ordering patch. |
| Contact form cramped or clipped | Remove duplicate horizontal padding from nested contact wrappers; use the Landed `#five` band as the contact band without a second padded section. Adjust the contact-column or field-grid breakpoint so controls fit; when a two-column field grid produces inputs under 160 CSS pixels wide, stack the fields. Verify label/control containment and inspect focused contact screenshots at desktop and mobile sizes, plus tablet measurements. | Preserve all source-identifiable non-upload fields and the assigned template signature. Do not hide fields, shrink text below readable size, or remove disclosures to make the form fit. |
| Forty tile grid | Add the two-column desktop grid override only when the selected Forty layout has at least three existing tiles and three media tiles, and browser QA measured fewer than two desktop columns. | Do not create tiles or assign unrelated images to fill the grid. If tile/media inventory is insufficient, regenerate. |
| Invalid or inappropriate images | Replace an image only with an exact approved source or category-fallback URL already present in candidate inputs, and only when the static checker identifies the invalid/unapproved URL or the report identifies the relevant image slot. Preserve provenance and record the substitution. | Never invent, search for, transform, or silently substitute a URL. If image pixels are unavailable, do not claim semantic relevance or replace the source URL speculatively; mark image content UNVERIFIED without blocking the native QA status. |
| CTA contrast | Use browser-measured failing CTA selectors to add a narrowly scoped high-contrast treatment. Exclude full-card tile-link overlays so the repair does not cover tile photography. | Do not change the assigned palette tokens or apply a broad rule that damages unrelated controls. Rerun computed contrast at desktop and mobile. |
| First-screen CTA placement | If browser QA proves the CTA is below the first screen, move/use the exact measured CTA label and safe verified destination in the hero, after the H1, only when the destination is allowed and matches source evidence. | Do not invent a CTA, label, destination, contact endpoint, or duplicate an unsafe/off-site action. If the CTA cannot be tied to verified source evidence, do not insert it. |
| Mobile navigation | Normalize a uniquely identified, correctly controlled mobile nav's hidden/open visibility and measured open/close, Escape, focus, and keyboard behavior. Apply only when the menu control and controlled nav relationship are unambiguous. | Do not guess IDs, add a second navigation system, or inject behavior into ambiguous markup. If the menu cannot be uniquely identified or behavior remains failing, regenerate/manual fix. |
| Contact form and contact channels | Restore a field only from the captured source form schema when its omission is unambiguous; align/group verified contact-channel CTAs or mark the source contact region when the failed check and existing markup identify the target. Preserve exact field order, labels, types, required state, and non-submitting preview semantics. | Never invent, rename, reorder, or change a source field; never add a submission endpoint or imply submission works. Ambiguous field mapping or a form behavior mismatch requires source review and regeneration. |
| Missing demo Send CTA | When captured source inquiry fields are already present and the only failure is the CTA, add one accessibly named, enabled `<button type="button">Send inquiry</button>` after the fields and place the existing/required no-send disclosure adjacent to the contact group. Rerun all required native static and desktop/mobile browser checks for the changed file. | Do not add a field, endpoint, confirmation implying success, or script that submits/stores data. If there is no source form schema or the contact controls are ambiguous, do not fabricate a form; use verified contact actions or regenerate from source evidence. |
| Other generated visual defects | Apply a documented, narrowly scoped CSS repair only for a measured browser defect with a known target (for example, a contrast or label treatment), then rerun. | “Looks wrong” alone is not a deterministic repair instruction. Do not alter source claims, imagery, template identity, content hierarchy, or form behavior without evidence. Report unresolved visual judgment as unverified; do not invent a defect or claim visual approval. |
| Broken in-page links or duplicate IDs | Add a missing ID to the existing, semantically correct target section or update the link to its clearly matching existing section; remove or rename a duplicate ID only when all references are unambiguous. | Do not point a link at a merely convenient but unrelated section. If the intended section is unclear, keep the check failed and request source/context or regenerate with an explicit section map. |

**Repair records and status**

For every candidate, record each attempted repair in `evidence/<candidate>/repairs.json`: triggering check IDs, measured problem, changed region, exact change, result (`APPLIED`, `NOT_NEEDED`, `FAILED`, or `BLOCKED`), before/after digest, evidence paths, and retest check IDs. Record a no-op as `NOT_NEEDED`; record an unsafe or unsupported fix as `BLOCKED`, not as success. Keep remaining failures and the final failure summary explicit.

Do not write `NOT_NEEDED` only because a check could not run. Use it only when no repairable defect was found in the checks that actually ran. Fix safe, independently verifiable defects before packaging; image visibility limitations do not alter native QA results.

**Mandatory retest rule:** After every repair pass, rerun all static/document checks that could be affected and the available native browser QA at 1440×900 desktop, 768×900 tablet, and 390×844 mobile against the changed final candidate. For changes to HTML, CSS, navigation, forms, layout, or CTA behavior, rerun all required native static and browser checks—not only the originally failing assertion. Capture new viewport and focused contact screenshots where required, update reports, recompute SHA-256, and invalidate prior QA results and screenshots until they are re-established for the new bytes. If no repair changed the file, record `NOT_NEEDED`; do not claim a retest was performed unless it actually ran.

### 6.4.2 Bounded candidate retries and slot selection

Generation is a slot-filling loop, not a one-shot request for three pages. Keep a candidate ledger at `evidence/candidate-ledger.json` and update it after every attempt, repair, retest, and continuation. Preserve all passing candidates and their evidence; retry only to fill a missing slot or replace a candidate that no longer qualifies. The authenticated skill session uses the smaller skill-mode limits below; do not apply the guest workflow's larger retry budget to skill runs.

**Attempt and continuation limits**

- Initial skill batch: generate one candidate per required slot (Forty, Landed, Story), for at most 3 attempts.
- If a slot still fails a blocking gate after its repair and retest opportunity, allow one targeted regeneration for that slot. The skill retry batch is capped at 3 additional attempts, for a hard maximum of 6 generations.
- Continue from the saved skill ledger and retained passing candidates. Do not reset attempt numbering, repeat a passing slot, or start an unbounded batch. The separate GitHub Actions workflow keeps its own 12-attempt initial and 12-attempt continuation limits; those apply only to workflow-mode records.
- Stop immediately once all three distinct slots have a qualified passing candidate. Do not spend remaining attempts on cosmetic alternatives.
- Count a candidate attempt when a new candidate generation is initiated for a slot. Repairs and retests belong to that attempt; they do not create a new candidate attempt. Record generation/setup failures too, with a failure status and summary.

**Ledger and pass-count rules**

Each ledger entry must include global attempt number, batch number and within-batch attempt, candidate ID/path, assigned slot/template/signature, status, whether it qualifies as a pass, failed check IDs, concise failure summary, repair/retest state, HTML digest, evidence paths, and whether it was retained or superseded. The ledger summary must include `execution_mode: "skill"`, target count (3), initial/continuation limits, total attempts and attempts per batch, passing count, passing slot IDs, missing slots, continuation eligibility/reason, and terminal status.

A candidate counts as passing only when its latest final QA/status record is PASS for its current HTML digest and its rendered template signature matches its assigned slot. Count distinct slots—not number of passing folders. Multiple passing attempts for one slot count as one slot filled; retain the best/latest qualifying candidate for that slot and mark other passing attempts as surplus, not as extra completion credit. Never infer a pass from a prior digest or from a partial QA run.

**Slot assignment and retaining successes**

- Slots are fixed: 1 = Forty, 2 = Landed, 3 = Story. Assign each new attempt to a currently missing slot. Among missing slots, prefer the least-attempted slot; break ties in stable slot order, rotating the tie-break start by global attempt number. Do not retry a slot already filled by a retained passing candidate unless that candidate is later invalidated or its evidence is found inconsistent.
- Retain every passing candidate and its complete evidence package across continuation. Do not regenerate or overwrite a passing candidate just to keep attempt numbering sequential. The final set must contain exactly one retained passing candidate from each slot.
- Feed the next attempt the previous attempt's concrete failure summary and relevant evidence: failed check IDs, measured defect/viewport, attempted repair and result, and unresolved issue. Preserve source facts, assigned template slot, and approved asset/contact constraints. Change the candidate only to address those findings; do not switch slots or weaken QA criteria to manufacture a pass.
- After any repair, apply the automated-repair retest rules in §6.4.1. A failed retest keeps the attempt nonpassing and informs the next generation attempt.

**Failure and stopping behavior**

For every unsuccessful attempt, record a concise actionable failure summary and preserve the original QA/repair evidence. Separate generation/tool/access failures from candidate-quality failures. Do not retry an access gate, rate limit, sign-in requirement, or service error as though it were an HTML defect; mark continuation blocked unless the workflow's continuation eligibility rules permit it. At the cap, return the retained passing candidates plus a clear list of missing slots and unresolved failure summaries. If fewer than three slots pass, report the run as incomplete/failed—not as a completed three-candidate deliverable set—and do not substitute a different template.
