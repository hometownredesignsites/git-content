### 2. Prepare and validate source assets
1. Extract candidate image URLs from the source site, including hero/project/service imagery. Record the exact URL, source page/section, discovery method, alt text, and any dimensions encoded in a CDN rendition. Use alt text and surrounding copy only as relevance hints; they are not proof of the unseen pixels. Do not mislabel logos/icons/tracking pixels as photographs. Treat requested pixel dimensions as evidence about that delivered rendition: a Wix `w_615`/`h_461` URL is capped at that size even if the original might be larger, and is generally too small for a full-width desktop hero.
2. Keep image evidence in distinct levels: URL discovered; image bytes retrieved and signature-validated; image pixels actually inspected; visual relevance/crop/alt accuracy reviewed; resolution judged for placement; reuse terms checked. Record only the highest level supported by evidence. A 200 response, MIME label, alt text, thumbnail preview, or URL alone cannot prove the next level. Do not bypass access controls or hotlink protections.
3. Match the preparer's actual source-image pipeline: it canonicalizes Wix media resize variants to the original media URL, resolves/deduplicates URLs using the workflow URL key, filters to the source host/recognized image CDNs and removes logo/icon/social/tracking/tiny candidates, then ranks by discovery method (`srcset`/lazy srcset first; rendered image and lazy attributes next; social metadata next; backgrounds next; plain `src` last). The preparer may validate at most 24 ranked distinct candidates and pass up to 3 with recognized image bytes. Its byte validation does not establish visual relevance or adequate resolution. Preserve both the discovered rendition URL and canonical original URL. The production HTML must use the canonical original URL for Wix assets; do not copy a resized page-thumbnail URL into `src` just because that is the URL exposed by the source page. The preparer may also include up to 3 category-pool fallback photos; do not describe these as dynamically searched stock results.
4. Apply the workflow's exact Wix canonicalization whenever the discovered URL has host `static.wixstatic.com` and a `/media/` path: retain the first path component after `/media/` (for example, `b9ad62_<asset-id>~mv2.jpg`) and build `https://static.wixstatic.com/media/<that-component>`, dropping the following `/v1/...` transform path and query string. Record the original discovered URL separately. This is URL normalization from an observed Wix URL, not a guessed asset ID. Apply it only to Wix; do not alter other CDN URLs. Put the canonical URL in the candidate HTML's `src` and in the external-review request's `canonical_url`. A candidate that uses an observed Wix `/v1/fit/` or `/v1/fill/` rendition when the canonical URL can be derived fails the limited `wix_images_use_canonical_source_url` check. Do not inline or embed image bytes as part of this rule. Canonicalization requests the original asset but does not prove its decoded dimensions; report resolution as UNVERIFIED until measured. If a CDN rendition is explicitly retained for a small thumbnail, record and justify that intended rendered size; never use a known small rendition for a placement larger than that rendition.
5. Judge pixel sufficiency against rendered placement only when source dimensions and the rendered image box are known. For a full-width hero, the source should be at least 1440 pixels wide; around 2× is preferable for high-density displays. Account for `cover` cropping and section aspect ratio. Record source, requested rendition, and rendered dimensions and a per-image resolution result. If bytes or source dimensions are unavailable, use `UNVERIFIED`; a CDN URL's requested width is a rendition clue, not a decoded-dimension measurement.
6. Preserve the exact source/canonical URL in production HTML; do not substitute a guessed, proxied, or newly constructed asset URL. Image-fetch failure does not block candidate generation. Record byte validation as `BLOCKED` or `UNVERIFIED`, resolution as `UNVERIFIED`, and image-content review as `EXTERNAL_PENDING` when a separate network-enabled process is expected. Do not claim workflow parity or image approval from those statuses.
7. When verified bytes are available in the same session, the official image-aware runner may create disposable embedded-image copies and validate signatures, hashes, and browser decode dimensions. Keep production HTML unchanged and temporary copies outside deliverables. When bytes are unavailable, render the original exact candidate anyway for structural/layout measurement; classify screenshots as layout-only if images are missing. Do not fabricate embedded copies, claim image-aware screenshots, or substitute unrelated images.
8. **Fallback behavior must match the current preparer; do not claim dynamic discovery.** The workflow uses fixed Unsplash pools rather than web/stock search. The exact 59 pools and 116 category mappings are bundled in `references/fallback-image-pools.json`, synchronized from `prepare_candidate_context.py` (source commit recorded in the file). Match a business category to its specific pool before a broad category; unmatched/suppressed categories receive no fallback. These are category-level mappings, not proof that any individual image is visually suitable. When GitHub is connected, compare the JSON against the current `prepare_candidate_context.py`; if it changed, use the current version only when the mapping and URLs can be read and recorded accurately.

**ChatGPT image access limitation:** Do not run a mandatory image GET before generation. Discover the source page's exact URLs and alt text, derive canonical Wix originals using rule 4, and use those canonical remote URLs in production HTML. Do not embed image bytes. If the ChatGPT session can display actual pixels or fetch bytes, record that as additional evidence. Otherwise create an external image-review request tied to final candidate hashes and include both discovered and canonical URLs; ask the external process to fetch the canonical URL. A network-enabled GitHub Action may verify reachability, signatures, dimensions, and render screenshots; actual semantic image relevance still requires a vision-capable reviewer and must be explicitly reported. External results count only when they identify the same candidate SHA-256 and image URLs.

**Known image-relevance gaps and suppressed fallbacks:** The selector intentionally provides no fixed fallback for aquarium maintenance, bakeries, donut shops, ice cream shops, candy shops, record stores, RV repair, small engine repair, automotive upholstery, farriers, shoe repair, dance studios, martial-arts schools, fishing guides, kayak/canoe rental, DJs, bounce-house rental, pool/spa stores, mattress stores, fireplace/stove shops, hobby/model shops, tent rental, photo booths, mini golf, go-kart tracks, indoor playgrounds, HVAC companies, plumbers, electricians, roofers, pest control, septic services, well services, garage-door companies, locksmiths, tree services, lawn-care companies, irrigation companies, performance shops, car audio installers, towing companies, mobile mechanics, custom farming, orchards, Christmas tree farms, pumpkin farms, agritourism businesses, limousine companies, tractor repair, agricultural-equipment repair, and hunting preserves. These categories were removed from misleading broad pools; use relevant source-site imagery where available and disclose when no fallback is available. Do not reintroduce a generic fallback until appropriate specialist assets are curated. Each pool is a curated static list, not a dynamically discovered result. The workflow does not open asset landing pages, resolve creators, inspect licenses/reuse terms, or visually observe the image. Its fallback check is a live image-byte/load check only; this is not proof of licensing, visual relevance, or suitability. Do not describe these assets as searched, license-verified, or visually reviewed.

The preparer currently checks and may pass up to 3 category-pool fallbacks **even when 3 source photos have been selected**. Preserve this behavior in the skill: source photos and fallback options are supplied together, and the generator chooses only assets appropriate to the section. Do not describe fallback selection as conditional on having fewer than three source photos. Do not infer that a fallback is needed simply because it is present.

Each fallback record must accurately expose the limits of the available evidence. Include: `url` (the exact pool URL), `alt` (the pool's descriptive label, not a claim of visual inspection), `source: "validated_fallback"`, `source_type: "fixed_category_pool"`, `source_page: ""` when no landing page was checked, `source_name` (Unsplash; creator unresolved), `license_or_terms: "Not checked by this workflow"`, `terms_checked: false`, `subject_observed: ""` unless someone actually inspected the image, `subject_description` (the pool label), `intended_business_or_section_fit` (category-level rationale only, clearly marked as unverified), and `validation_status` (byte/load validation only). Include `fallback_search_status: "not_performed_fixed_pool_only"`, an empty `fallback_search_queries` list, and a reason explaining that dynamic search is not implemented. Do not invent a source page, creator, license, search query, observed subject, or visual-fit finding.

If the matching fixed pool has no entry or no fallback passes its image-byte/load check, report the fallback as unavailable; do not silently use an unrelated category or replace it with a web-search result. Dynamic stock discovery and reuse-terms verification are not implemented, so mark those requirements BLOCKED/UNVERIFIED rather than claiming feature parity. The expanded catalog mappings improve category relevance but do not establish that an individual image is visually suitable or licensed for reuse.
9. Extract and verify the source logo. Use it when available and appropriate; preserve aspect ratio and do not recreate or fabricate a logo. If none can be verified, use a text wordmark based on the verified business name and report that no source logo was found.
