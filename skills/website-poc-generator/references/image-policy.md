### 2. Prepare and validate source assets
1. Extract candidate image URLs from the source site, including hero/project/service imagery. Inspect the image or its available metadata; reject logos/icons used as photography, tracking pixels, tiny thumbnails, unrelated assets, and images that do not support the business or section. Treat requested pixel dimensions as quality evidence: a Wix `w_615`/`h_461` variant is capped at that size even if the underlying original is larger, and is generally too small for a full-width desktop hero. Do not mistake a low-resolution delivery variant for proof that the source photograph itself is low resolution.
2. **Fetch and validate source-image bytes, not just image URLs.** The preparer performs an HTTP GET with an 8-second timeout, follows redirects, and inspects up to the first 65,536 response bytes for a recognized image signature; HTTP status and response content type are recorded as evidence, not treated alone as proof. The candidate context must carry the exact approved asset URL, source page, source provenance, discovery method, source type, and validation evidence: request method, timeout, requested/final URL, HTTP status, content type, bytes inspected, result, and validated boolean. A 200 response containing HTML or a MIME header alone is not proof of an image. Do not bypass access controls or hotlink protections. If direct fetching is unavailable, use a real browser image-load check only when actually performed and label its evidence distinctly; otherwise mark validation BLOCKED/UNVERIFIED.
3. Match the preparer's actual source-image pipeline: it canonicalizes Wix media resize variants to the original media URL, resolves/deduplicates URLs using the workflow URL key, filters to the source host/recognized image CDNs and removes logo/icon/social/tracking/tiny candidates, then ranks by discovery method (`srcset`/lazy srcset first; rendered image and lazy attributes next; social metadata next; backgrounds next; plain `src` last). It validates at most 24 ranked distinct candidates and passes up to 3 that return recognized image bytes. The preparer does not automatically establish visual relevance or adequate resolution; the generator must inspect the supplied image/metadata and judge whether it fits the business and section. Keep byte-load validation, resolution suitability, crop quality, and visual relevance as separate findings. Preserve the exact canonical approved URL passed by the preparer in generated HTML; retain the original discovered URL separately if available. The preparer may also include up to 3 validated category-pool fallback photos; do not describe these as dynamically searched stock results.
4. For Wix URLs, follow the workflow's specific canonicalization: use the original `/media/<asset-id>` URL represented by the discovered resize variant, and record both the discovered URL and canonical URL. Do not keep a clearly undersized resize URL for a large hero merely because it loads; do not invent an asset ID or alter URLs for other CDNs. When a CDN exposes `srcset`/size variants, prefer a verified source that can serve enough pixels for its intended placement, and use responsive variants when available and validated. If no adequately sized source variant is evidenced, use a different approved image or mark hero resolution UNVERIFIED/BLOCKED; do not upscale a thumbnail and call image quality passed.
5. Judge pixel sufficiency against the rendered placement. For a full-width hero, use a source at least as wide as the largest required desktop viewport (1440 CSS px); prefer roughly 2× that width for high-density displays when available. Account for `cover` cropping and section aspect ratio: source pixel width alone does not prove the crop has enough usable resolution or keeps the subject. For cards and spotlights, compare source dimensions to the largest measured rendered image box. Record known source dimensions, requested CDN dimensions, intended/rendered dimensions, and the resolution finding (`PASS`, `FAIL`, or `UNVERIFIED`) per image. If dimensions cannot be measured, say so and keep resolution UNVERIFIED.
6. Preserve the approved/canonical source URL in the generated page; do not substitute a guessed, proxied, or newly constructed asset URL outside the Wix canonicalization above. A byte fetch is validation, not permission to claim the image is locally bundled. If the runtime cannot fetch image bytes or load images in a browser, mark byte validation BLOCKED/UNVERIFIED; if it cannot determine adequate pixel dimensions, mark resolution UNVERIFIED. Disclose these capability gaps and do not claim workflow parity.
7. Browser screenshot QA uses a disposable HTML copy in which every exact image URL used by the production candidate is replaced with a data URI made from the fetched bytes. Include `src`, `srcset`, `picture/source`, lazy-image attributes, posters, inline styles, and embedded CSS backgrounds. Require successful HTTP responses, recognized image signatures, nonempty bounded data, byte digests, and browser-decoded natural dimensions. Keep the production HTML's original URLs and digest unchanged. Keep the embedded copy and image bytes in a temporary directory outside the deliverable and commit package. Any unresolved or unavailable image blocks image-aware screenshots and visual QA; captures can be retained only as layout diagnostics. Do not substitute a category fallback or unrelated image to make the screenshot gate pass.
7. **Fallback behavior must match the current preparer; do not claim dynamic discovery.** The workflow uses fixed Unsplash pools rather than web/stock search. The exact 59 pools and 116 category mappings are bundled in `references/fallback-image-pools.json`, synchronized from `prepare_candidate_context.py` (source commit recorded in the file). Match a business category to its specific pool before a broad category; unmatched/suppressed categories receive no fallback. These are category-level mappings, not proof that any individual image is visually suitable. When GitHub is connected, compare the JSON against the current `prepare_candidate_context.py`; if it changed, use the current version only when the mapping and URLs can be read and recorded accurately.

**Known image-relevance gaps and suppressed fallbacks:** The selector intentionally provides no fixed fallback for aquarium maintenance, bakeries, donut shops, ice cream shops, candy shops, record stores, RV repair, small engine repair, automotive upholstery, farriers, shoe repair, dance studios, martial-arts schools, fishing guides, kayak/canoe rental, DJs, bounce-house rental, pool/spa stores, mattress stores, fireplace/stove shops, hobby/model shops, tent rental, photo booths, mini golf, go-kart tracks, indoor playgrounds, HVAC companies, plumbers, electricians, roofers, pest control, septic services, well services, garage-door companies, locksmiths, tree services, lawn-care companies, irrigation companies, performance shops, car audio installers, towing companies, mobile mechanics, custom farming, orchards, Christmas tree farms, pumpkin farms, agritourism businesses, limousine companies, tractor repair, agricultural-equipment repair, and hunting preserves. These categories were removed from misleading broad pools; use relevant source-site imagery where available and disclose when no fallback is available. Do not reintroduce a generic fallback until appropriate specialist assets are curated. Each pool is a curated static list, not a dynamically discovered result. The workflow does not open asset landing pages, resolve creators, inspect licenses/reuse terms, or visually observe the image. Its fallback check is a live image-byte/load check only; this is not proof of licensing, visual relevance, or suitability. Do not describe these assets as searched, license-verified, or visually reviewed.

The preparer currently checks and may pass up to 3 category-pool fallbacks **even when 3 source photos have been selected**. Preserve this behavior in the skill: source photos and fallback options are supplied together, and the generator chooses only assets appropriate to the section. Do not describe fallback selection as conditional on having fewer than three source photos. Do not infer that a fallback is needed simply because it is present.

Each fallback record must accurately expose the limits of the available evidence. Include: `url` (the exact pool URL), `alt` (the pool's descriptive label, not a claim of visual inspection), `source: "validated_fallback"`, `source_type: "fixed_category_pool"`, `source_page: ""` when no landing page was checked, `source_name` (Unsplash; creator unresolved), `license_or_terms: "Not checked by this workflow"`, `terms_checked: false`, `subject_observed: ""` unless someone actually inspected the image, `subject_description` (the pool label), `intended_business_or_section_fit` (category-level rationale only, clearly marked as unverified), and `validation_status` (byte/load validation only). Include `fallback_search_status: "not_performed_fixed_pool_only"`, an empty `fallback_search_queries` list, and a reason explaining that dynamic search is not implemented. Do not invent a source page, creator, license, search query, observed subject, or visual-fit finding.

If the matching fixed pool has no entry or no fallback passes its image-byte/load check, report the fallback as unavailable; do not silently use an unrelated category or replace it with a web-search result. Dynamic stock discovery and reuse-terms verification are not implemented, so mark those requirements BLOCKED/UNVERIFIED rather than claiming feature parity. The expanded catalog mappings improve category relevance but do not establish that an individual image is visually suitable or licensed for reuse.
5. Extract and verify the source logo. Use it when available and appropriate; preserve aspect ratio and do not recreate or fabricate a logo. If none can be verified, use a text wordmark based on the verified business name and report that no source logo was found.
