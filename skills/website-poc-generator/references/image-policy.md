### 2. Prepare and validate source assets
1. Extract candidate image URLs from the source site, including hero/project/service imagery. Record the exact URL, source page/section, discovery method, alt text, and any dimensions encoded in a CDN rendition. Use alt text and surrounding copy only as relevance hints; they are not proof of the unseen pixels. Do not mislabel logos/icons/tracking pixels as photographs. Treat requested pixel dimensions as evidence about that delivered rendition: a Wix `w_615`/`h_461` URL is capped at that size even if the original might be larger, and is generally too small for a full-width desktop hero.
2. Keep image evidence in distinct levels: URL discovered; image bytes retrieved and signature-validated; image pixels actually inspected; visual relevance/crop/alt accuracy reviewed; resolution judged for placement; reuse terms checked. Record only the highest level supported by evidence. A 200 response, MIME label, alt text, thumbnail preview, or URL alone cannot prove the next level. Do not bypass access controls or hotlink protections.
3. Match the preparer's actual source-image pipeline: it canonicalizes Wix media resize variants to the original media URL, resolves/deduplicates URLs using the workflow URL key, filters to the source host/recognized image CDNs and removes logo/icon/social/tracking/tiny candidates, then ranks by discovery method (`srcset`/lazy srcset first; rendered image and lazy attributes next; social metadata next; backgrounds next; plain `src` last). The preparer may validate at most 24 ranked distinct candidates and pass up to 3 with recognized image bytes. Its byte validation does not establish visual relevance or adequate resolution. Preserve both the discovered rendition URL and canonical original URL. The production HTML must use the canonical original URL for Wix assets; do not copy a resized page-thumbnail URL into `src` just because that is the URL exposed by the source page. The preparer may also include up to 3 category-pool fallback photos; do not describe these as dynamically searched stock results.
4. Apply the workflow's exact Wix canonicalization whenever the discovered URL has host `static.wixstatic.com` and a `/media/` path: retain the first path component after `/media/` (for example, `b9ad62_<asset-id>~mv2.jpg`) and build `https://static.wixstatic.com/media/<that-component>`, dropping the following `/v1/...` transform path and query string. Record the original discovered URL separately. This is URL normalization from an observed Wix URL, not a guessed asset ID. Apply it only to Wix; do not alter other CDN URLs. Put the canonical URL in the candidate HTML's `src` and retain both URLs in source evidence. A candidate that uses an observed Wix `/v1/fit/` or `/v1/fill/` rendition when the canonical URL can be derived fails the limited `wix_images_use_canonical_source_url` check. Do not inline or embed image bytes as part of this rule. Canonicalization requests the original asset but does not prove its decoded dimensions; report resolution as UNVERIFIED until measured. If a CDN rendition is explicitly retained for a small thumbnail, record and justify that intended rendered size; never use a known small rendition for a placement larger than that rendition.
5. Judge pixel sufficiency against rendered placement only when source dimensions and the rendered image box are known. For a full-width hero, the source should be at least 1440 pixels wide; around 2× is preferable for high-density displays. Account for `cover` cropping and section aspect ratio. Record source, requested rendition, and rendered dimensions and a per-image resolution result. If bytes or source dimensions are unavailable, use `UNVERIFIED`; a CDN URL's requested width is a rendition clue, not a decoded-dimension measurement.
6. Preserve the exact source/canonical URL in production HTML; do not substitute a guessed, proxied, or newly constructed asset URL. Image-fetch failure does not block candidate generation. For this ChatGPT skill, record image-byte validation, image-content review, and resolution as `UNVERIFIED` when unavailable. These are informational and do not block native QA. Do not claim the image was inspected or approved.
7. For ChatGPT-native QA, do not fetch, cache, or embed remote image bytes. Render the exact production HTML for structural/layout measurements; if remote images remain unavailable, classify screenshots as layout-only. Never substitute unrelated images or claim image-aware screenshots.
8. **Fallback behavior must match the current preparer; do not claim dynamic discovery.** The workflow uses fixed Unsplash pools rather than web/stock search. Match a business category to its specific pool before a broad category; unmatched/suppressed categories receive no fallback. These are category-level mappings, not proof that any individual image is visually suitable. When GitHub is connected, compare the JSON against the current `prepare_candidate_context.py`; if it changed, use the current version only when the mapping and URLs can be read and recorded accurately.

**ChatGPT image access limitation:** Do not run a mandatory image GET before generation.
