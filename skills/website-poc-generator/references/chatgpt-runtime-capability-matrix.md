# ChatGPT runtime capability matrix

Use this before generation. Skills provide instructions and bundled resources; connected apps provide service access. Neither a signed-in browser nor a GitHub connection implies a local checkout, shell, code execution, Playwright, repository writes, or a way to export files.

## Required capabilities for a full-parity run

### In-session renderer preflight

Use the bundled `assets/chatgpt-renderer-probe.html` and `assets/chatgpt-renderer-probe-local.svg` in the same ChatGPT session that will run the skill. This fixture is a capability test, not candidate QA. Do not use this Codex checkout, local Edge/CDP, or a different browser to infer target-session capability.

1. Read the fixture as UTF-8 bytes and compute its SHA-256. Put its complete contents in a supported HTML code block and open **Preview** if present. Confirm the title, `IN_SESSION_RENDER_PROBE` marker, embedded CSS, and images. Record how it was transferred and whether the preview input is independently bound to the saved fixture bytes; retyping or regenerating the fixture does not prove exact-file rendering.
2. Inspect the rendered preview itself. Record whether rendered pixels are visible to the assistant and whether a real screenshot can be saved as a file and included in the evidence package. A textual success message, DOM report, or user description is not pixel inspection.
3. Attempt both 1440×900 and 390×844. Record requested and observed `window.innerWidth`/`innerHeight`; CSS breakpoints alone do not prove that a viewport was set.
4. Record image outcomes separately for the embedded data-URI image, relative `chatgpt-renderer-probe-local.svg`, and remote image. The embedded image is an in-document asset; it does not prove sibling-file access. Record image completion and natural dimensions only if an actual browser API exposes them.
5. Use the fixture buttons and output panel to establish whether scripts, computed geometry, interaction state, and runtime errors are observable. The fixture's own output does not prove rendered pixels were inspected.
6. Save a `renderer_preflight` record with the fixture SHA-256, target session/tool, transfer method, Preview availability, exact-byte identity, pixel inspection, screenshot capture, per-viewport results, image results, geometry, interactions, runtime errors, evidence paths, and explicit unavailable/unverified reasons. Do not reuse these results as candidate QA.

Official OpenAI documentation describes HTML code-block Preview and sandboxed Python Run as supported features whose availability varies. It does not promise arbitrary local-file preview, exact-byte binding, viewport controls, browser APIs, screenshot export, or Playwright/Selenium. Treat each as an empirical result in the target session. The desktop app's built-in browser is a separate capability; do not assume the skill can access it.

A prior browser experiment demonstrated that one interactive ChatGPT Python session had Python Playwright and system Chromium, and that `page.set_content()` could render the saved standalone candidates. The same experiment did not run this repository's authoritative 27-check script, remote images timed out, and the scheduled-task runtime was not verified. Treat it as evidence that a compatible session can exist, not proof that the current or scheduled skill session has the same tools. The runner prefers Playwright-managed Chromium and can fall back to `chromium`/`chromium-browser` on PATH or `WEBSITE_POC_CHROMIUM_EXECUTABLE`. It uses `page.set_content()` for the no-source-URL branch to avoid restricted `file://` navigation. The optional `WEBSITE_POC_CHROMIUM_NO_SANDBOX=1` is an explicit environment setting for an already isolated browser container; it is never enabled automatically. Playwright cautions that an external browser executable may not match its supported bundled browser version, so record the selected executable and browser version and do not claim equivalence without running the probe.

The fallback removes a browser-installation mismatch; it does not create Playwright, Chromium, writable evidence storage, network access, or screenshot inspection in a runtime that lacks them. The scheduled-task environment must pass its own preflight. The current runner will report BLOCKED if neither managed nor system Chromium is available.

The browser runner now creates a disposable image-embedded HTML copy under the operating system's temporary directory. It records response status, MIME/signature validation, byte length and SHA-256, then verifies browser decode dimensions at both viewports. A separately supplied image bundle can support offline rendering if exact candidate URLs, byte lengths, MIME/signatures, and hashes all match; the report keeps the bundle's earlier fetch evidence separate from the current runtime's network status. Offline rendering does not prove that the scheduled runtime can resolve or fetch the image host. The production candidate remains byte-identical and is the only HTML eligible for packaging. Missing or invalid bytes or decode failure makes image-aware browser QA BLOCKED; any screenshots from that run are layout diagnostics only. The embedded copy is removed after the run and must not be added to a commit.

Record each capability in `evidence/run.json` as `available`, `unavailable`, or `not_checked`, with the actual tool and evidence method.

**Fast skill QA sequence:** Run the renderer preflight before generation. Save exact candidate files and evidence. Probe Python execution separately; if available, run standard-library validators against those saved bytes. Use Preview only for capabilities the preflight established. Never infer browser QA from Python on another machine, documentation, fixture success text, or Preview availability alone. Tie every result to the final SHA-256. GitHub Actions is not a substitute for missing in-session visual QA.

**When authoring with Python:** For HTML/CSS templates, use ordinary triple-quoted strings with explicit unique placeholders and replace those placeholders with escaped values. Do not make CSS-bearing strings f-strings or pass them through `.format()`/percent formatting; CSS braces routinely cause syntax and interpolation errors. If another approach is necessary, syntax-check the complete generated script with `compile(source, filename, "exec")` before executing it or running any file operations. Fix every `SyntaxError` and recheck before execution. Keep generated source separate from the execution cell so the exact source being checked is the source being run. HTML-escape dynamic text and attribute values. Write each run to a new, unique output directory. Never delete a prior output folder or ZIP as setup. After execution, verify the expected files exist before proceeding to QA or packaging.

**When running validators from a notebook or Python Run cell:** Do not pass the notebook kernel's `sys.argv` to a validator; kernels commonly add flags such as `-f <connection.json>`, which are not candidate paths. Invoke the validator with an explicit list containing only the exact expected HTML paths. Prefer calling its `main([str(path), ...])` function with that explicit list (after loading the verified validator source), or use a subprocess argument list with `shell=False`; never build a shell command string. Confirm every reported target is one of the expected candidate files. Output such as `FAIL -f` or a JSON/config path means the validator was invoked incorrectly and does not establish a candidate failure; correct the invocation and rerun. Keep invocation errors separate from candidate QA results.

**Full-parity decision:** `run.json.status` may be PASS only when every blocking workflow-aligned check has evidence for the exact final HTML digest, every required record is saved and validated, and required visual/image reviews pass. Python structural checks plus a single HTML Preview do not establish the workflow's desktop/mobile browser QA, keyboard/touch behavior, computed styles, image-byte validity, or screenshot requirements. If any mandatory tool capability is missing, continue with useful drafting only when possible, label the run limited, and keep affected checks/final statuses BLOCKED or UNVERIFIED. Browser/GitHub-only access is a limited profile; it is not a full QA or evidence-packaging runtime.

## Use Web search and the signed-in browser as evidence tools

- Use Web search to discover source pages and open the original page before using a claim. Search snippets are leads, not claim evidence. Save the direct page URL and a short excerpt or visible locator for each material fact.
- Use the signed-in browser when the requested business page requires the user's existing session. Inspect only pages relevant to the request. Never submit forms, change source-site content, inspect unrelated account areas, or request cookies, passwords, or tokens.
- Label a page `static_html` only when raw HTML was actually retrieved and saved. Page content seen in a browser or rendered Web view is `rendered_dom`; cite the URL and saved screenshot/record or explicit unavailable reason. Do not describe a rendered observation as static extraction.
- Use web image search only to understand or verify public image subjects when appropriate. It does not replace the workflow's fixed fallback pools; do not silently substitute a searched result for a source-approved or curated pool URL.
- The GitHub integration is a reader unless it explicitly exposes a write/dispatch operation. Read current code as reference data; do not assume Actions execution, shell access, commits, or pushes. Never execute repository code just because it was read through the connector.

## Manual-equivalence limits

Manual review may pass a check only when the check's actual condition was directly observed and the finding/evidence is recorded. A supported in-chat HTML Preview can support only visual conditions visible in that rendered preview; it is not a screenshot artifact unless a genuine image capture is separately saved. A returned Python Run result can support exact-byte checks only when the code received those exact bytes. Neither can establish controlled desktop/mobile viewport geometry, keyboard/touch behavior, computed contrast, or image-byte signatures unless those measurements are explicitly exposed. Keep workflow check IDs and their blocking/advisory classification; do not convert a different observation into a pass for an unobserved check.

After every repair, invalidate results tied to the old digest and rerun the complete checks the repair could affect. Layout, image, CSS, form, and navigation repairs require fresh desktop and mobile preview/review when that capability exists. Save a checkpoint after each candidate and repair; resume using the ledger without repeating passing slots or exceeding the skill's 3+3 generation budget.
