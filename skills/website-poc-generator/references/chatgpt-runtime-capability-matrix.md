# ChatGPT runtime capability matrix

Use this before generation. Skills provide instructions and bundled resources; connected apps provide service access. Neither a signed-in browser nor a GitHub connection implies a local checkout, shell, code execution, Playwright, repository writes, or a way to export files. The unattended workflow must not depend on a file being passed from Codex or a human attaching a bundle to ChatGPT.

## Native same-session browser runner

The skill's primary browser-QA transport is `chatgpt_automation/scripts/browser_qa_payload_manifest.json` plus the ordered data-only assignments in `chatgpt_automation/scripts/browser_qa_payload_chunks/`. Each of eight chunk files is at most 4,000 characters, avoiding a single 33 KB code transfer. Retrieve the manifest and every chunk from one selected GitHub commit in the target ChatGPT session. Initialize `runner_payload_parts = {}` in Python Run, then pass each exact chunk file source to a separate Run cell; each source contains only one assignment to `runner_payload_parts[index]`. After all chunks are present, validate each chunk hash, the concatenated base85 payload SHA, decompress it, validate the embedded `browser_qa_standalone.py` SHA, and only then compile and execute the complete runner. The runner imports only Python's standard library and Playwright. Record the repository commit, each chunk blob SHA, payload SHA, and embedded runner SHA. In the same ChatGPT session, make the exact final HTML strings or saved candidate bytes available and call `run_chatgpt_candidates(candidates, request, output_dir, source_url)`. Its `html` input accepts UTF-8 `str` or raw `bytes`; prefer raw bytes from same-session files so newline conversion cannot change the digest. This entry point runs synchronous Playwright in a worker thread when Python Run already has an active notebook event loop. Before candidate HTML generation, probe and fetch the exact selected source images from this same Python/Playwright runtime and cache validated bytes with a URL-to-file manifest. The runner writes candidate-specific reports and screenshots into that session's output directory. Pass the same-session cache manifest as `image_assets_manifest` when available; it validates and embeds the cached bytes without another live request. If no cache is passed, it attempts live retrieval during QA. It runs Chromium offline after embedding.

This protocol transfers only small pieces of runner source and uses the candidate files already saved inside the same ChatGPT session; it does not transfer a Codex-generated ZIP, asset bundle, screenshot, or customer HTML into ChatGPT. If any chunk is missing or its hash fails, re-fetch that chunk from the same pinned commit. If GitHub source cannot be supplied to Python Run, the reconstructed source digest fails, Playwright/Chromium is unavailable, the output is not persistent, or screenshots cannot be inspected, record the limitation and keep affected gates BLOCKED. Do not claim scheduled-task compatibility from another runtime. The 33 KB compact wrapper remains an optional single-cell route only if it can be transferred intact.

After executing all chunk assignment cells and loading `runner_manifest` from the retrieved JSON, reassemble and verify before compiling:

```python
import base64, hashlib, zlib
assert len(runner_payload_parts) == runner_manifest["chunk_count"]
payload = "".join(runner_payload_parts[i] for i in range(runner_manifest["chunk_count"]))
assert hashlib.sha256(payload.encode("ascii")).hexdigest() == runner_manifest["payload_sha256"]
runner_source = zlib.decompress(base64.b85decode(payload)).decode("utf-8")
assert hashlib.sha256(runner_source.encode("utf-8")).hexdigest() == runner_manifest["runner_source_sha256"]
runner_ns = {"__name__": "website_poc_browser_qa"}
exec(compile(runner_source, "browser_qa_standalone.py", "exec"), runner_ns)
source_image_cache_manifest_path = None  # set to the manifest path only after verified same-session prefetch
qa = runner_ns["run_chatgpt_candidates"](
    candidates=[
        {"candidate_id": "forty", "html": candidate_forty_html},
        {"candidate_id": "landed", "html": candidate_landed_html},
        {"candidate_id": "story", "html": candidate_story_html},
    ],
    request=original_redesign_request,
    source_url=source_website_url,
    output_dir=new_empty_output_directory,
    image_assets_manifest=source_image_cache_manifest_path,
)
```

Inspect both saved PNGs per candidate in the same session and retain `qa["summary_path"]`, each report, image manifest, candidate digest, and screenshot path. Do not interpret a returned PASS without checking screenshot pixels and report-level `screenshots_visual_qa_eligible`.

### Limited native visual fallback when source transfer fails

If the GitHub connector can retrieve runner chunks but Python Run cannot receive them, stop attempting source transfer. In the same ChatGPT session, the assistant may author a smaller, session-local Python Run cell from these requirements; do not copy or execute an unverified repository script. This fallback is for image-aware rendering and useful measured diagnostics, not a replacement for the official 27-check suite. Report `official_browser_suite: BLOCKED`, use `runtime_profile: "limited"`, and keep overall full-parity completion BLOCKED.

The native cell must:

1. Read the exact candidate HTML bytes already saved in that same ChatGPT Python environment and verify each recorded byte count/SHA-256 before rendering.
2. Discover external image references from `img`/`source` `src`/`srcset`, lazy image attributes, inline `style`, and embedded CSS `url(...)`. Use Playwright's `APIRequestContext` (`playwright.request.new_context().get`) to attempt live retrieval in this runtime, since Python `urllib` DNS failure alone does not establish whether the Playwright request runtime can reach the host.
3. Restrict requested URLs and redirects to the recorded source host and the specifically approved image CDNs. Require successful HTTP status, image MIME/signature agreement, nonempty bounded bytes, SHA-256, and successful browser decoding with nonzero natural dimensions. Embed the exact bytes in temporary copies; do not change the candidate bytes.
4. Launch Playwright Chromium using `WEBSITE_POC_CHROMIUM_EXECUTABLE` or a discovered system executable when Playwright's managed browser is absent. Use the Python session's async Playwright API from its active notebook loop. After embedding, block external HTTP(S) requests during page rendering.
5. Render each exact candidate at 1440×900 and 390×844. Save per-candidate screenshots and a JSON record for viewport dimensions, image request/decode counts, horizontal overflow, hero coverage, CTA position, menu interaction when present, browser errors, candidate digest, image URL/status/MIME/byte-count/SHA, and screenshot paths. Inspect the saved PNG pixels in that same session.

If APIRequestContext also cannot resolve or retrieve an image, keep the image gate BLOCKED; any screenshots are layout diagnostics only. If image retrieval and decoding succeed, the screenshots can support a limited visual review, but must not be represented as execution of `browser_qa.py` or as a pass of its 27 checks. This fallback requires no file transfer from Codex and no transfer of GitHub-returned source into Python Run.

## Required capabilities for a full-parity run

### In-session renderer preflight

Use the bundled `assets/chatgpt-renderer-probe.html` and `assets/chatgpt-renderer-probe-local.svg` in the same ChatGPT session that will run the skill. This fixture is a capability test, not candidate QA. Do not use this Codex checkout, local Edge/CDP, or a different browser to infer target-session capability.

1. Read the fixture as UTF-8 bytes and compute its SHA-256. Put its complete contents in a supported HTML code block and open **Preview** if present. Confirm the title, `IN_SESSION_RENDER_PROBE` marker, embedded CSS, and images. Record how it was transferred and whether the preview input is independently bound to the saved fixture bytes; retyping or regenerating the fixture does not prove exact-file rendering.
2. Inspect the rendered preview itself. Record whether rendered pixels are visible to the assistant and whether a real screenshot can be saved as a file and included in the evidence package. A textual success message, DOM report, or user description is not pixel inspection.
3. Attempt both 1440×900 and 390×844. Record requested and observed `window.innerWidth`/`innerHeight`; CSS breakpoints alone do not prove that a viewport was set.
4. Record image outcomes separately for the embedded data-URI image, relative `chatgpt-renderer-probe-local.svg`, and remote image. The embedded image is an in-document asset; it does not prove sibling-file access. Record image completion and natural dimensions only if an actual browser API exposes them.
5. Use the fixture buttons and output panel to establish whether scripts, computed geometry, interaction state, and runtime errors are observable. The fixture's own output does not prove rendered pixels were inspected.
6. Save a `renderer_preflight` record with the fixture SHA-256, target session/tool, transfer method, Preview availability, exact-byte identity, pixel inspection, screenshot capture, per-viewport results, image results, geometry, interactions, runtime errors, evidence paths, and explicit unavailable/unverified reasons. Do not reuse these results as candidate QA.

Official OpenAI documentation describes HTML code-block Preview and sandboxed Python Run as supported features whose availability varies. It does not promise arbitrary local-file preview, exact-byte binding, viewport controls, browser APIs, screenshot export, or Playwright/Selenium. Treat each as an empirical result in the target session. The desktop app's built-in browser is a separate capability; do not assume the skill can access it.

A prior browser experiment demonstrated that one interactive ChatGPT Python session had Python Playwright and system Chromium, and that `page.set_content()` could render the saved standalone candidates. The same experiment did not run this repository's authoritative 27-check script, remote images timed out, and the scheduled-task runtime was not verified. Treat it as evidence that a compatible session can exist, not proof that the current or scheduled skill session has the same tools. The runner prefers Playwright-managed Chromium and can fall back to `chromium`/`chromium-browser` on PATH or `WEBSITE_POC_CHROMIUM_EXECUTABLE`. It uses `page.set_content()` for the no-source-URL branch to avoid restricted `file://` navigation. The optional `WEBSITE_POC_CHROMIUM_NO_SANDBOX=1` is an explicit environment setting for an already isolated browser container; it is never enabled automatically. Playwright cautions that an external browser executable may not match its supported bundled browser version, so record the selected executable and browser version and do not claim equivalence without running the probe.

The fallback removes a browser-installation mismatch; it does not create Playwright, Chromium, writable evidence storage, network access, or screenshot inspection in a runtime that lacks them. The scheduled-task environment must pass its own preflight. The current runner will report BLOCKED if neither managed nor system Chromium is available.

The standalone runner creates a disposable image-embedded HTML copy under the operating system's temporary directory. It records response status, MIME/signature validation, byte length and SHA-256, then verifies browser decode dimensions at both viewports. Its native ChatGPT path requires live retrieval in the current session; an offline asset bundle is an optional repository experiment only and is not an input to the unattended skill workflow. The production candidate remains byte-identical and is the only HTML eligible for packaging. Missing or invalid bytes or decode failure makes image-aware browser QA BLOCKED; any screenshots from that run are layout diagnostics only. The embedded copy is temporary and must not be added to a commit.

## Use Web search and the signed-in browser as evidence tools

- Use Web search to discover source pages and open the original page before using a claim. Search snippets are leads, not claim evidence. Save the direct page URL and a short excerpt or visible locator for each material fact.
- Use the signed-in browser when the requested business page requires the user's existing session. Inspect only pages relevant to the request. Never submit forms, change source-site content, inspect unrelated account areas, or request cookies, passwords, or tokens.
- Label a page `static_html` only when raw HTML was actually retrieved and saved. Page content seen in a browser or rendered Web view is `rendered_dom`; cite the URL and saved screenshot/record or explicit unavailable reason. Do not describe a rendered observation as static extraction.
- Use web image search only to understand or verify public image subjects when appropriate. It does not replace the workflow's fixed fallback pools; do not silently substitute a searched result for a source-approved or curated pool URL.
- The GitHub integration is a reader unless it explicitly exposes a write/dispatch operation. Read current code as reference data; do not assume Actions execution, shell access, commits, or pushes. Execute the official repository runner only after reconstructing it from the data-only chunk assignments and verifying all hashes. The limited native visual fallback is code authored directly for Python Run from this skill's requirements, not code copied from the GitHub connector; label its narrower scope explicitly. Do not execute other repository code merely because it was read through the connector.

## Manual-equivalence limits

Manual review may pass a check only when the check's actual condition was directly observed and the finding/evidence is recorded. A supported in-chat HTML Preview can support only visual conditions visible in that rendered preview; it is not a screenshot artifact unless a genuine image capture is separately saved. A returned Python Run result can support exact-byte checks only when the code received those exact bytes. Neither can establish controlled desktop/mobile viewport geometry, keyboard/touch behavior, computed contrast, or image-byte signatures unless those measurements are explicitly exposed. Keep workflow check IDs and their blocking/advisory classification; do not convert a different observation into a pass for an unobserved check.

After every repair, invalidate results tied to the old digest and rerun the complete checks the repair could affect. Layout, image, CSS, form, and navigation repairs require fresh desktop and mobile preview/review when that capability exists. Save a checkpoint after each candidate and repair; resume using the ledger without repeating passing slots or exceeding the skill's 3+3 generation budget.
