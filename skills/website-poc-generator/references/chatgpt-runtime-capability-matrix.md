# ChatGPT runtime capability matrix

Use this before generation. Skills provide instructions and bundled resources; connected apps provide service access. Neither a signed-in browser nor a GitHub connection implies a local checkout, shell, code execution, Playwright, repository writes, or a way to export files. The unattended workflow must not depend on a file being passed from Codex or a human attaching a bundle to ChatGPT.

## Native same-session browser runner

The ChatGPT runtime-supported browser runner is transported by `chatgpt_automation/scripts/browser_qa_payload_manifest.json` plus the ordered data-only assignments in `chatgpt_automation/scripts/browser_qa_payload_chunks/`. Retrieve the manifest and every chunk from one selected GitHub commit in the target ChatGPT session, verify every chunk and reconstructed source digest, then compile and execute the complete runner. Record the repository commit, chunk blob SHAs, payload SHA, and runner SHA. Run it with exact final HTML bytes authored or saved in that same session. It runs the viewport/layout, geometry, contrast, template, and interaction checks that do not require external image or font retrieval. Four network-dependent checks (`hero_image_loads_desktop_and_mobile`, `visible_content_images_load_in_browser`, `images_load_in_browser`, and `fonts_load_in_browser`) are reported separately as `EXTERNAL_PENDING`; they are not part of the ChatGPT runtime-supported pass gate. Image/content validation remains a distinct external review. The workflow's full 27-check result remains separate and must be reported UNVERIFIED unless that exact suite is actually executed.

This protocol uses candidate files already saved inside the same ChatGPT session; it does not transfer a Codex-generated ZIP, asset bundle, screenshot, or customer HTML into ChatGPT. If a chunk is missing or its hash fails, make one targeted re-fetch; then stop the runner path if it remains unavailable and continue with limited native checks where possible. If GitHub source cannot be supplied to Python Run, report the ChatGPT runner status as UNVERIFIED. If Python/Chromium or exact saved bytes are unavailable, block only the checks that depend on them. Do not claim scheduled-task compatibility from another runtime. The compact single-file wrapper remains an optional route only if it transfers intact.

After executing all chunk assignment cells and loading `runner_manifest` from the retrieved JSON, reassemble and verify before compiling:

```python
import base64, hashlib, zlib
assert len(runner_payload_parts) == runner_manifest["chunk_count"]
payload = "".join(runner_payload_parts[i] for i in range(runner_manifest["chunk_count"]))
assert hashlib.sha256(payload.encode("ascii")).hexdigest() == runner_manifest["payload_sha256"]
runner_source = zlib.decompress(base64.b85decode(payload)).decode("utf-8")
assert hashlib.sha256(runner_source.encode("utf-8")).hexdigest() == runner_manifest["runner_source_sha256"]
runner_ns = {"__name__": "website_poc_browser_qa"}
exec(compile(runner_source, "browser_qa_standalone.py", "exec"), runner_ns)
source_image_cache_manifest_path = None  # set to the manifest path only after verified same-session prefetch
qa = runner_ns["run_chatgpt_candidates"](
    candidates=[
        {"candidate_id": "forty", "html": candidate_forty_html},
        {"candidate_id": "landed", "html": candidate_landed_html},
        {"candidate_id": "story", "html": candidate_story_html},
    ],
    request=original_redesign_request,
    source_url=source_website_url,
    output_dir=new_empty_output_directory,
    image_assets_manifest=source_image_cache_manifest_path,
)
```

Inspect both saved PNGs per candidate in the same session and retain `qa["summary_path"]`, each report, image manifest, candidate digest, and screenshot path. Do not interpret a returned PASS without checking screenshot pixels and report-level `screenshots_visual_qa_eligible`.

### Limited native structure and layout assessment

If the hash-verified ChatGPT runner cannot be transferred and verified, stop attempting source transfer. In the same ChatGPT session, use a small session-local Python Run cell based on the checks below; do not copy or execute an unverified repository script. This lane is intentionally independent of image downloads. It verifies whether the generated document is structurally sound and whether its layout skeleton, measured geometry, and interactions work when rendered in the available Chromium. Record `runtime_profile: "limited"`, `native_limited_status: "PASS"` or the accurate failing status, the ChatGPT runner status as `UNVERIFIED` if not executed, `official_27_check_status: "UNVERIFIED"` unless that suite actually ran, and `external_image_content_status: "EXTERNAL_PENDING"` when a digest-bound handoff exists. This is a successful limited generation/structure assessment when it passes, not full workflow QA or image-aware approval.

The native cell must:

1. Read the exact candidate HTML bytes saved in the same ChatGPT Python environment. Verify byte count and SHA-256 before analysis and again before reporting.
2. Use Python's standard-library `html.parser` (or another parser already available in-session) to check doctype/document closure, `lang`, nonempty title, viewport metadata, exactly one main and H1, nonempty embedded CSS, unique IDs, resolvable same-page fragments, named buttons, labeled form controls, and absence of unintended local-file dependencies. Record the checks actually executed; do not call a subset the full static suite.
3. Inventory every image reference in `<img>`, `<source>`, `srcset`, lazy attributes, inline style, and embedded CSS `url(...)`. For each Wix URL, derive the canonical original by retaining the first media path component after `/media/` and dropping the trailing rendition transform (for example, `/v1/fill/...`); record both the discovered and canonical URLs and put the canonical URL in the candidate HTML. Do not embed bytes. Record alt text, source page/section, discovery method, and any rendition dimensions. Treat alt as a relevance hint only. Do not repeatedly probe a known-unreachable image host and do not make retrieval a precondition for generation.
4. Launch Playwright Chromium using `WEBSITE_POC_CHROMIUM_EXECUTABLE` or an existing executable discovered on PATH if managed Chromium is absent. Use `page.set_content(exact_html)` or another empirically available route that accepts the exact saved bytes. Use the active notebook loop correctly (`await main()` when a loop is already running); do not use `asyncio.run()` inside it. Wait for DOM readiness, not network idle, because external images may never resolve.
5. Render each candidate at 1440×900 and 390×844. At both sizes, record Chromium/version, viewport dimensions, main/hero/section rectangles, document scroll width, horizontal overflow, navigation and CTA visibility, template signature geometry, menu interaction (open/close/Escape) when present, console/runtime errors, and image request/response/decode results. Capture screenshots tied to the exact HTML digest and inspect the PNG pixels if the session exposes them. Mark all missing-image captures `layout_only_missing_remote_images`; do not score image composition or image visual review from them.
6. A candidate passes the limited native lane only if the exact-byte/static structure checks pass and all applicable geometry/interaction checks in this limited protocol pass at both viewports. A run passes only when all three template slots pass and the three recorded HTML digests match the delivered files. Image loading, image bytes, image subject, crop, resolution, licensing, and full 27-check execution remain separate statuses.

For a Python contrast-pair check, iterate over the mapping values, then assert the numeric ratios: `contrast_values = [contrast(*pair_fn(palette_for_slot)) for pair_fn in contrast_pairs.values()]`; `all(value >= 4.5 for value in contrast_values)`. Iterating over `mapping.items()` yields `(key, value)` tuples, so comparing each tuple to `4.5` raises `TypeError`; this is a check-cell bug, not a browser-suite result.
7. Write `evidence/native-limited-assessment.json` with each candidate ID/path/byte count/SHA, executed checks and results, viewport metrics, screenshot paths and classification, and run status. Include a check that every Wix candidate URL is canonical, not a transformed thumbnail. Write `evidence/external-image-review-request.json` with the same candidate digest plus each discovered URL, canonical URL used in HTML, alt text, source provenance, intended section, and known dimensions. Ask the external process to fetch the canonical URL. The handoff is a request, not evidence that the process ran.

If Chromium is unavailable but exact-byte static checks run, report `static_structure_status: PASS` where warranted and `native_limited_status: BLOCKED` for the missing rendered checks. If image requests fail, this does not block a passing limited structure/layout assessment, but `external_image_content_status` stays `EXTERNAL_PENDING`; images must not be called reviewed. This path requires no transfer from Codex and no transfer of GitHub-returned runner source into Python Run.

## Required capabilities for a full-parity run

### In-session renderer preflight

Use the bundled `assets/chatgpt-renderer-probe.html` and `assets/chatgpt-renderer-probe-local.svg` in the same ChatGPT session that will run the skill. This fixture is a capability test, not candidate QA. Do not use this Codex checkout, local Edge/CDP, or a different browser to infer target-session capability.

1. Read the fixture as UTF-8 bytes and compute its SHA-256. Put its complete contents in a supported HTML code block and open **Preview** if present. Confirm the title, `IN_SESSION_RENDER_PROBE` marker, embedded CSS, and images. Record how it was transferred and whether the preview input is independently bound to the saved fixture bytes; retyping or regenerating the fixture does not prove exact-file rendering.
2. Inspect the rendered preview itself. Record whether rendered pixels are visible to the assistant and whether a real screenshot can be saved as a file and included in the evidence package. A textual success message, DOM report, or user description is not pixel inspection.
3. Attempt both 1440×900 and 390×844. Record requested and observed `window.innerWidth`/`innerHeight`; CSS breakpoints alone do not prove that a viewport was set.
4. Record image outcomes separately for the embedded data-URI image, relative `chatgpt-renderer-probe-local.svg`, and remote image. The embedded image is an in-document asset; it does not prove sibling-file access. Record image completion and natural dimensions only if an actual browser API exposes them.
5. Use the fixture buttons and output panel to establish whether scripts, computed geometry, interaction state, and runtime errors are observable. The fixture's own output does not prove rendered pixels were inspected.
6. Save a `renderer_preflight` record with the fixture SHA-256, target session/tool, transfer method, Preview availability, exact-byte identity, pixel inspection, screenshot capture, per-viewport results, image results, geometry, interactions, runtime errors, evidence paths, and explicit unavailable/unverified reasons. Do not reuse these results as candidate QA.

Official OpenAI documentation describes HTML code-block Preview and sandboxed Python Run as supported features whose availability varies. It does not promise arbitrary local-file preview, exact-byte binding, viewport controls, browser APIs, screenshot export, or Playwright/Selenium. Treat each as an empirical result in the target session. The desktop app's built-in browser is a separate capability; do not assume the skill can access it.

A prior browser experiment demonstrated that one interactive ChatGPT Python session had Python Playwright and system Chromium, and that `page.set_content()` could render the saved standalone candidates. The same experiment did not run this repository's authoritative 27-check script, remote images timed out, and the scheduled-task runtime was not verified. Treat it as evidence that a compatible session can exist, not proof that the current or scheduled skill session has the same tools. The runner prefers Playwright-managed Chromium and can fall back to `chromium`/`chromium-browser` on PATH or `WEBSITE_POC_CHROMIUM_EXECUTABLE`. It uses `page.set_content()` for the no-source-URL branch to avoid restricted `file://` navigation. The optional `WEBSITE_POC_CHROMIUM_NO_SANDBOX=1` is an explicit environment setting for an already isolated browser container; it is never enabled automatically. Playwright cautions that an external browser executable may not match its supported bundled browser version, so record the selected executable and browser version and do not claim equivalence without running the probe.

The fallback removes a browser-installation mismatch; it does not create Playwright, Chromium, writable evidence storage, network access, or screenshot inspection in a runtime that lacks them. The scheduled-task environment must pass its own preflight. The current runner will report BLOCKED if neither managed nor system Chromium is available.

When image bytes are available, the official runner may create a disposable image-embedded HTML copy, record response/MIME/signature/byte/hash evidence, and verify browser decode dimensions. When they are unavailable, the runner's image-aware lane is BLOCKED, but this does not block candidate generation or the limited native structure/layout assessment. The production candidate remains byte-identical and is the only HTML eligible for delivery. Screenshots with missing images are layout-only diagnostics. Temporary copies and image bytes are never included in deliverables.

Record each capability in `evidence/run.json` as `available`, `unavailable`, or `not_checked`, with the actual tool and evidence method.

**Fast skill QA sequence:** Probe the actual target session, generate and save exact candidate files, and record their byte counts/SHA-256. Run the verified official suite when available; otherwise run the limited static and Chromium checks above. Tie every result to the final digest. A network-enabled GitHub Action can supplement same-digest image retrieval/decode/content review, but its result is separate from in-session candidate structure/layout assessment and must not be assumed to have run.

**When authoring with Python:** For HTML/CSS templates, use ordinary triple-quoted strings with explicit unique placeholders and replace those placeholders with escaped values. Do not make CSS-bearing strings f-strings or pass them through `.format()`/percent formatting; CSS braces routinely cause syntax and interpolation errors. If another approach is necessary, syntax-check the complete generated script with `compile(source, filename, "exec")` before executing it or running any file operations. Fix every `SyntaxError` and recheck before execution. Keep generated source separate from the execution cell so the exact source being checked is the source being run. HTML-escape dynamic text and attribute values. Write each run to a new, unique output directory. Never delete a prior output folder or ZIP as setup. After execution, verify the expected files exist before proceeding to QA or packaging.

**When invoking the chunked runner from Python Run:** Transfer and execute one verified data-only assignment per cell, then validate per-chunk, payload, and decompressed-source SHA-256 against the pinned manifest before compiling the full runner source. Do not pass the notebook kernel's `sys.argv`; call `run_chatgpt_candidates(...)` with exactly three `{candidate_id, html}` entries (`forty`, `landed`, `story`), the source URL, original request, and a new output directory. If candidate files were saved earlier in this same ChatGPT session, read raw bytes with `Path.read_bytes()` and compare their SHA-256 values with the session's recorded digests; pass those bytes directly without copying files from another app. Confirm output HTML SHA-256 matches the exact input bytes and each report names the correct candidate. Invocation or transfer errors are not candidate failures; correct them and rerun. Keep invocation errors separate from candidate QA results.

**Separate status decision:** `native_limited_status` may be PASS when the three exact candidate files pass the limited static and available Chromium checks described above, even if image requests fail. `official_27_check_status` and `external_image_content_status` remain separate. `run.json.status` and per-candidate full `final_status` may be PASS only when every required full-parity gate passes for the exact final digest, including image and visual reviews. Use `EXTERNAL_PENDING` for image review handed to a separate process but not yet returned; use BLOCKED when a required capability is unavailable and no valid limited status covers the user-facing goal. Do not confuse a successful limited generation/structure result with full visual approval.

## Use Web search and the signed-in browser as evidence tools

- Use Web search to discover source pages and open the original page before using a claim. Search snippets are leads, not claim evidence. Save the direct page URL and a short excerpt or visible locator for each material fact.
- Use the signed-in browser when the requested business page requires the user's existing session. Inspect only pages relevant to the request. Never submit forms, change source-site content, inspect unrelated account areas, or request cookies, passwords, or tokens.
- Label a page `static_html` only when raw HTML was actually retrieved and saved. Page content seen in a browser or rendered Web view is `rendered_dom`; cite the URL and saved screenshot/record or explicit unavailable reason. Do not describe a rendered observation as static extraction.
- Use web image search only to understand or verify public image subjects when appropriate. It does not replace the workflow's fixed fallback pools; do not silently substitute a searched result for a source-approved or curated pool URL.
- The GitHub integration is a reader unless it explicitly exposes a write/dispatch operation. Read current code as reference data; do not assume Actions execution, shell access, commits, or pushes. Execute the official repository runner only after reconstructing it from the data-only chunk assignments and verifying all hashes. The limited native visual fallback is code authored directly for Python Run from this skill's requirements, not code copied from the GitHub connector; label its narrower scope explicitly. Do not execute other repository code merely because it was read through the connector.

## Manual-equivalence limits

Manual review may pass a check only when the check's actual condition was directly observed and the finding/evidence is recorded. A supported in-chat HTML Preview can support only visual conditions visible in that rendered preview; it is not a screenshot artifact unless a genuine image capture is separately saved. A returned Python Run result can support exact-byte checks only when the code received those exact bytes. Neither can establish controlled desktop/mobile viewport geometry, keyboard/touch behavior, computed contrast, or image-byte signatures unless those measurements are explicitly exposed. Keep workflow check IDs and their blocking/advisory classification; do not convert a different observation into a pass for an unobserved check.

After every repair, invalidate results tied to the old digest and rerun the complete checks the repair could affect. Layout, image, CSS, form, and navigation repairs require fresh desktop and mobile preview/review when that capability exists. Save a checkpoint after each candidate and repair; resume using the ledger without repeating passing slots or exceeding the skill's 3+3 generation budget.
