# Wix Image Retrieval Diagnostics

Determine which retrieval paths in the **active target session** can see, retrieve, or decode a small set of Wix-hosted images. This is a diagnostic skill, not website generation or full visual QA. Keep it independent of `website-poc-generator`; do not edit candidate HTML or its skill.

When ChatGPT Web/search or a signed-in browser is available, it may be used as a separate comparison path to open the source page or display an image preview. If image pixels or a thumbnail are visibly present in returned content or an inspected screenshot, record `web_visual_preview: visible` even when clicking/opening the exact source URL returns an error. Record source-to-preview correspondence separately as verified or unverified; do not label a displayed preview NOT VISIBLE merely because direct URL opening failed. Seeing a photograph in a web result or browser does not prove its raw bytes are available to Python or can be saved for embedding. Claim byte retrieval only when a tool actually returns the bytes to the same session and they pass image validation.

## Inputs and boundaries

- Use the exact image URLs supplied by the user or observed on the named source website. If none are supplied, discover source images using available read-only page tools and choose at most three representative URLs.
- Run diagnostics in the same ChatGPT session and Python environment that reported the failure. Results from Codex, another chat, a local browser, or a downloaded bundle do not establish target-session capability.
- Test HTTPS URLs only. Keep requests limited to the observed Wix image host(s); do not crawl the site's entire media library.
- Use an isolated request context without user cookies or authorization headers. Do not submit forms, change the source site, alter system DNS, install packages, or bypass an environment's network policy.
- Do not use hardcoded CDN IP addresses. Do not disable TLS verification (`ignore_https_errors`, `curl -k`, `--insecure`, or `http.sslVerify=false`).

## Diagnostic sequence

1. Record the current runtime and available methods: Python, Playwright `APIRequestContext`, optional Pillow/browser image decoding, optional `curl`, and whether Playwright-managed Chromium or an existing system Chromium executable is available. Do not infer availability from a different session.
2. For each exact URL, record its sanitized URL and hostname. Probe name resolution once with Python `socket.getaddrinfo` for the default family and IPv4 (`AF_INET`); probe IPv6 (`AF_INET6`) when available. Bound each lookup to a few seconds when the runtime permits, and do not repeat a timed-out lookup. Record returned addresses or the precise exception/timeout. These probes distinguish resolver failure from a later connection failure; they do not prove an HTTP connection works.
3. If Playwright is available, create the request context with supported context options only (for example, `timeout` and `ignore_https_errors=False`); `max_retries` is a request option, not a `new_context` option. Make one bounded GET per selected image with redirects disabled (`max_redirects=0`) and, if the installed version supports it, `max_retries=0`. If `max_retries` is unsupported, omit it because the API default is no network retries; record the version. A `TypeError` during context or request setup means no HTTP request was made and must not be reported as DNS failure. Record status, content type, `Location`, error type/message, and response byte count when present. Follow redirects manually only when each hop is HTTPS and remains on an observed or explicitly approved image host; cap the chain at three hops. If this version cannot stop automatic redirects, do not treat its final response as redirect-validated. Do not repeatedly retry the same failed host.
4. If the APIRequestContext request fails and Chromium can launch, try one exact URL through Chromium's normal image-loading path. Use the Playwright-managed browser, or an already installed system Chromium via `executable_path`; do not install a browser. Attach `request`, `response`, `requestfailed`, and console listeners before setting the image URL. Create a minimal page with an empty `<img id='probe'>`, then assign the exact URL as an evaluation argument (not interpolated HTML). Record `getAttribute('src')`, `img.src`, and, after a bounded wait, `currentSrc`, `complete`, `naturalWidth`, and `naturalHeight`. Require the `src` attribute/property to equal the requested URL and record whether a request event actually started. If `currentSrc` is empty and no request event occurred, classify the browser attempt as `request_not_started/setup_unverified`, not a Wix or DNS failure. If a request starts, record its response/final URL or exact failure; `net::ERR_NAME_NOT_RESOLVED` is DNS evidence, while a pending request at timeout is unresolved. If available, read the corresponding Playwright `Response.body()` bytes and validate them. Keep TLS verification enabled and reject unapproved redirect hosts. Browser visibility without readable response bytes proves Chromium image display, not Python byte access.
5. If Playwright is unavailable or both Playwright request paths fail, optionally make one `urllib` request as a separate client comparison. Use curl only under the current-IPv4 condition below. Label each client separately; success in one does not imply another works. In a notebook with an active loop, call the async probe with `await probe()`; do not use `asyncio.run()` inside that loop. A setup exception is not a DNS result.
6. If ordinary DNS returns a current IPv4 address but Playwright's request fails at name resolution, and `curl` is available in this same Python environment, make one comparison request with curl's `--resolve <host>:443:<that-current-ip>`. Keep the original `https://<host>/...` URL so hostname and certificate checks remain active. Do not use a raw-IP URL or guessed/stale address. If the current runtime has no resolved IP, stop this fallback; report DNS as blocked. Use a DoH resolver only if the target environment explicitly permits it, and report it as a separate resolver path rather than silently overriding DNS.
7. Validate retrieved bytes independently of HTTP status or `Content-Type`: require a successful response, nonempty bounded bytes, a recognized image signature consistent with the MIME type, SHA-256, and decoded nonzero width and height. Prefer Pillow when installed; otherwise use a browser image decode only if a browser actually launches in this session. Record unavailable validation separately; never infer image validity from a URL or page screenshot.
8. Save a compact JSON report and temporary image bytes only when the current session has a writable temporary location. Include timestamp, runtime/tool, exact or safely redacted URL, each DNS family result; separate APIRequestContext, Chromium image-loading, urllib, and curl outcomes; DOM `src` attribute/property, `currentSrc`, and request-started status; redirect chain; HTTP status, MIME/signature result, byte count, SHA-256, decoded dimensions, `web_visual_preview` (`visible`, `not_visible`, or `not_assessed`), source-to-preview correspondence (`verified`, `unverified`, or `not_applicable`), and the outcome/reason for every step. Do not persist cookies, credentials, or sensitive query values. If file output is unavailable, return the same report inline.

## Optional metadata-only relevance assessment

When source-page text is available but image pixels are not, assess relevance from metadata as a separate, lower-confidence result. Record the exact `alt` text, caption/title, nearby heading or section, image URL/media ID, page location, capture method, and source locator. Compare those words with the business service and intended section; label the finding `likely_relevant`, `likely_mismatch`, or `unknown`, and state the evidence and confidence.

Metadata can support a semantic relevance estimate; it cannot confirm the actual photo contents, quality, crop, resolution, licensing, or that the image matches its alt text. Missing alt text means metadata is unavailable, not that the image is irrelevant. Never report a metadata-only estimate as visual inspection.

## Optional thumbnail-to-review-copy proof

Use this section only when the user asks whether an image-aware, nonproduction review copy is feasible. It tests the proposed mechanism; it is not candidate generation or final visual QA.

1. Start with a source-linked thumbnail for one selected image. Record whether ChatGPT receives actual image pixels in its Web/browser output and whether the visible preview is reliably associated with the Wix media ID. A screenshot supplied by the user can be visually analyzed, but it is not a thumbnail retrieval result for this session.
2. Separately determine whether the exact thumbnail bytes are accessible to the same session's Python/file-writing tools. A Web preview or model-visible image alone is not byte access. Do not recreate, approximate, screenshot-crop, or base64-encode guessed pixels. Do not use an unrelated search result or a proxy thumbnail without verified mapping to the selected Wix asset.
3. If the exact bytes are available, validate their MIME/signature, dimensions, and SHA-256, then create a minimal temporary HTML fixture containing only that image as a data URI. Do not include the production candidate or remote resources. Open/render it only if this same session exposes a preview or browser and inspect the actual rendered image pixels.
4. Report separate outcomes for `web_visual_preview`, `source_to_preview_match`, `thumbnail_bytes_in_python`, `review_fixture_created`, and `review_fixture_visual_inspection`. A successful fixture proves only that the review-copy mechanism works for the tested thumbnail. It does not verify full-resolution assets, the production HTML, image crop/resolution quality, or the website's desktop/mobile QA.
5. Keep the fixture and thumbnail bytes in a temporary session-local location. Do not deliver, commit, or use them to replace production image URLs. If raw thumbnail bytes cannot enter the Python session, stop at visual preview analysis and report the review-copy construction as blocked.
## Interpret results

Use `PASS` only when every selected image was retrieved through Playwright `APIRequestContext` and its image signature, MIME, hash, and decoded dimensions were verified. Use `PASS_BROWSER` when each exact image loaded and decoded in Chromium and the response bytes were also retrieved and validated. Use `PASS_FALLBACK` when those checks pass only through an approved same-session alternate transport; this does not establish that a downstream Playwright-only runner can retrieve the images. Use `PARTIAL` when only some selected images pass, `BLOCKED` when DNS or network policy prevents retrieval, and `FAIL` when a response is received but is invalid or cannot be decoded as an image. Keep the per-URL outcomes visible; an overall label never replaces them.

- **Chromium request not observed:** the test did not establish that the exact URL was assigned and requested. Correct the setup and rerun once; do not report DNS or Wix failure from an empty `currentSrc` alone.
- **DNS blocked:** no usable address from the permitted resolver path. Do not label the URL invalid and do not invent an address.
- **Resolver-path difference:** ordinary/APIRequestContext DNS fails but a current IPv4 answer plus `curl --resolve` succeeds with TLS verification. Report that narrowly as a client/resolver-path difference; it is not proof that Playwright itself can retrieve the image.
- **Connection/TLS blocked:** DNS returned an address, but connection or certificate validation failed. Keep this distinct from DNS failure.
- **HTTP blocked or rejected:** a response arrived but its status or redirect host is unacceptable. Do not treat it as valid image bytes.
- **Image validation failed:** the response was not a valid decodable image or its MIME/signature disagreed.
- **Retrieval verified:** exact bytes were retrieved and their signature, MIME, digest, and decoded dimensions were checked. This establishes asset availability only; it does not establish visual relevance, licensing, crop suitability, or responsive layout quality.
- **Preview visible, direct URL blocked:** image pixels appeared in Web/browser output, but opening the exact source URL failed. Report visual preview as visible and byte retrieval separately as blocked or unavailable; only mark the source correspondence verified when the output reliably associates that preview with the exact source asset.

Do not create or change website candidates, and do not modify `website-poc-generator`. A minimal temporary one-image review fixture is allowed only when the user requests the optional proof above; it is not a deliverable or QA pass. Report the evidence and stop. A successful alternate-client fetch may justify a later, separately authorized change to a consumer workflow; it does not silently change that workflow's pass criteria.
